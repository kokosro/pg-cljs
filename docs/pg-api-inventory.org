* About this document

This is the verified inventory of the external surface that pg-cljs wraps: the npm
package =pg= (node-postgres) 8.23.1 and the packages it is made of. It is research
only; implementation happens in later phases, and section 11 states the consequences
each fact has for the pg-cljs design.

*Product constraint that shapes everything below:* the finished library is
ClojureScript-only at every call site: no =^js= hints, no JS interop outside ONE binding
namespace, kebab-case keyword maps in and out with VALUES never touched, promesa
promises for every async operation, core.async channels for the notification stream
(sliding buffer 1024 default), structured =ex-info= errors with =:type=
=:pg-cljs/<kind>=, nothing chosen on the caller's behalf, and zero runtime npm
dependencies beyond =pg=.

** What pg-cljs WILL wrap
- =Client=: construction from a config map / the PG* environment / a connection
  string, =connect=, =query= (text + values, and the config-object form with =name=,
  =row-mode=, =types=, =query-timeout=), =end=, =getTransactionStatus=, the =error=,
  =end=, =notification=, =notice= events.
- =Pool=: construction, =connect= + =release= (plain, with error, with =true=),
  =query=, =end=, the counters (=totalCount= / =idleCount= / =waitingCount= /
  =expiredCount=), the =connect= / =acquire= / =release= / =remove= / =error= events.
- The query =Result= and =Field= objects (section 2.5-2.6), multi-statement results.
- LISTEN/NOTIFY: the =notification= event as a core.async channel.
- Type parsers: reading what =pg= yields as-is (section 4), registering a custom text
  parser per client / per query (the =types= option) and globally (=pg.types=).
- =DatabaseError= fields, socket errors and the =pg=-generated error strings as one
  structured taxonomy (section 8).
- =escapeIdentifier= / =escapeLiteral= as pure helpers.

** What pg-cljs will NOT wrap (inventoried for completeness, deliberately out)
- The =Query= object / "submittable" protocol (=pg-cursor=, =pg-query-stream=), the
  =row= event streaming mode, =client.cancel=, portal paging (=rows= option).
- The callback forms of every method (=pg-cljs= uses the promise forms only).
- Pipeline mode (=pipeline: true=, pg 8.17+): inventoried (2.4.6), not exposed in the
  first phases; a later phase may add it as an option after a live round-trip.
- =pg-native= / =pg.native= / =NODE_PG_FORCE_NATIVE=; =pg-cloudflare= runtime; the
  deprecated =pgpass= lookup and the =Promise= constructor option; =client.ref/unref=;
  COPY (=pg-copy-streams=); binary result mode (=binary: true=); =replication=.
- SSL file reading from a connection string (=sslcert= / =sslkey= / =sslrootcert= read
  files from disk inside =pg-connection-string=): the library never reads a file; it
  passes an =ssl= map through and documents that the string form may read files.

** Reading conventions
- Upstream names are given verbatim (=connectionTimeoutMillis=, =statement_timeout=,
  =rowCount=); upstream mixes camelCase and snake_case, and the kebab-case translation
  table lives in section 11.1.
- "Client" is =pg.Client= (the pure-JS =lib/client.js=); "Pool" is =pg.Pool= (=pg-pool=
  bound to that Client, =pg/lib/index.js:13-19=).
- Promise semantics are those of the no-callback call forms; every method also takes
  a Node callback as its last argument, which pg-cljs will not use.

* 2. Client

** 2.1 Construction: =new Client(config)=
=[SRC pg/lib/client.js:51-117]=. =config= may be omitted, a string (a connection
string, parsed as a whole: =connection-parameters.js:55=) or an object. Construction
never connects and never throws for connection problems; it throws synchronously only
for an invalid =sslnegotiation= (=connection-parameters.js:105-112=; =[OFFLINE]=
messages in 8.3).

Resolution order for each connection parameter (=connection-parameters.js:9-23=
=val()=): the config value if truthy → the environment variable → the default of
=pg/lib/defaults.js=. NOTE =if (config[key])=: a falsy config value (=0=, =""=,
=false=) is treated as absent and falls through to the environment.

=connectionString= (=connection-parameters.js:59-61=): the parsed string is
=Object.assign=-ed OVER the config object, so every key the parser emits overrides the
same key given directly — including keys the string does NOT contain: the parser emits
=port: ''= and =database: null= when the URL has none, which then fall through to
env/default. =[OFFLINE]=: ={connectionString: "postgres://a@b/c", port: 9999, host:
"ignored?"}= yields host =b=, port =5432=, user =a=, database =c=.

** 2.3 =client.connect()=
=[SRC client.js:232-247]=: without a callback, returns a native Promise that RESOLVES
WITH THE CLIENT itself (=resolve(this)=, =:243=; =[OFFLINE]= =r === client=) once the
backend sends ReadyForQuery (=client.js:373-387=; the =connect= event is emitted then,
=:386=), or REJECTS with:
- the Node socket error (e.g. =ECONNREFUSED=, section 8.2) or the TLS error,
- the backend =DatabaseError= of a failed authentication / startup
  (=_handleErrorWhileConnecting=, =:400-411= — the error message that arrives while
  connecting goes to the connect callback, not the =error= event),
- =Error('timeout expired')= when =connectionTimeoutMillis= elapses (=:167-171=; the
  timer destroys the socket, the rejection message is ="timeout expired"=;
  =[OFFLINE]=), NOTE the timer is =unref()='d (=:173-175=): a process with nothing
  else alive exits before it fires (=[OFFLINE]= observed with a fake socket; a real
  =net.Socket= keeps the loop alive, so this bites only fakes),
- =Error('Connection terminated unexpectedly')= when the socket closes mid-handshake
  without an earlier error (=:203-224=),
- =Error('Client has already been connected. You cannot reuse a client.')= on a second
  =connect()= — also after =end()=: a Client is single-use (=:158-164=; =[OFFLINE]=).
- =TypeError('Password must be a string')= when a password FUNCTION resolves a
  non-string (=:283=); a rejecting password function rejects connect with its error
  (=:292-294=).

=password= as a function =[SRC client.js:276-294]= =[DOC features/connecting]=: called
with the =ConnectionParameters= when the server asks for a password, may return a
string or a promise of one; =undefined= means "no password". Startup parameters sent
=[SRC client.js:543-572]= =[OFFLINE]=: =user=, =database=, =application_name= (or the
fallback), =replication=, =statement_timeout= / =lock_timeout= /
=idle_in_transaction_session_timeout= (as integer strings), =options=; the Connection
adds =client_encoding= (=UTF8= default).

Queries may be issued BEFORE =connect()= resolves: they queue and run once the client
is ready (=client.js:782-783=, =_pulseQueryQueue= gated on =readyForQuery=;
=[OFFLINE]= a query issued before =connect()= resolved with =command "SELECT"=).

*** 2.4.3 Queueing and ordering
One query at a time per client: new queries wait in =_queryQueue= and run in order
(=client.js:616-641=). Since 8.x, calling =query()= while one is active prints a
one-time deprecation warning ("Calling client.query() when the client is already
executing a query is deprecated and will be removed in pg@9.0", =:34-37,779-781=)
unless =pipeline= is on. Consequence in 11.3: pg-cljs must not rely on upstream
queueing; the caller sequences, or the pool is used.

*** 2.4.4 =query_timeout=
=[SRC client.js:702-737]=: when set (per query or per client), a timer rejects the
query with =Error('Query read timeout')=, removes it from the queue if not yet sent,
and in pipeline mode destroys the connection if already sent. The connection is NOT
cancelled server-side in non-pipeline mode: the backend keeps running the statement
and the client stays blocked until it finishes (flagged 10.2).

** 3.2 =pool.connect()= and =client.release(...)=
=[SRC pg-pool/index.js:190-238,240-309,335-366,369-429]= =[OFFLINE]=:
- resolves with a =Client= that carries a =release= function (=:342=); an idle client
  is handed out on =process.nextTick= (=:201-204=), a new one is created when the pool
  is not full, otherwise the request queues FIFO (=:207,231=).
- =release()= returns =undefined= and returns the client to the idle set.
- =release(err)= (truthy; =[DOC apis/pool]= documents it as =release(destroy?:
  boolean)=): the client is ENDED and removed (=:392-398=); =true= works the same
  (=[OFFLINE]= =totalCount= 0 after both).
- a second =release()= on the same checkout THROWS synchronously
  ="Release called on client which has already been released to the pool."=
  (=:26-28,369-380=).
- a client is also removed on release when the pool is ending, when it is not
  queryable, when it is ending, when =maxUses= is reached, or when its lifetime
  expired (=:392-405=).
- while idle, a client =error= is caught by the pool's idle listener (=:51-64=): the
  client is removed and the pool emits =error(err, client)= with =err.client= set to
  the client; =[OFFLINE]= observed =['error', 'socket died', client]= followed by
  =remove=.
- after =pool.end()=, =connect()= rejects ="Cannot use a pool after calling end on the
  pool"= (=:191-194=).
- queue wait timeout: rejects ="timeout exceeded when trying to connect"= (=:224=);
  new-client connect timeout: rejects ="Connection terminated due to connection
  timeout"= with =cause= (=:276=); a refused connection rejects with the socket
  error (=[OFFLINE]= =ECONNREFUSED=, =totalCount= 0 afterwards).

** 3.3 =pool.query(text, values)=
=[SRC pg-pool/index.js:431-486]= =[OFFLINE]=: checks out a client, runs ONE query,
releases it and resolves with the Result. When the query fails the client is

counts went from =[1 1]= to =[0 0]=; so every failed =pool.query= costs a

="Passing a function as the first parameter to pool.query is not supported"=. The
config-object form works too (=client.query= receives it unchanged; =[OFFLINE]=
with a =values= array).

** 3.4 =pool.end()=

* 7. LISTEN/NOTIFY mechanics
=[DOC apis/client]= =[SRC client.js:271,535-537]= =[OFFLINE]=:
- A connection subscribes with a normal query ="LISTEN <channel>"= and unsubscribes
  with ="UNLISTEN <channel>"= / ="UNLISTEN *"=; the server pushes
  =NotificationResponse= messages asynchronously on THAT connection, which the Client
  re-emits as the =notification= event with the payload of 2.8.1.
- Sending: ="NOTIFY <channel>, 'payload'"= or =SELECT pg_notify($1, $2)= (the latter
  takes parameters; channel names in =NOTIFY= are identifiers and cannot be bound).
  A notification sent by the same connection is delivered to it too (=[OFFLINE]= the
  fake pushed it while the =NOTIFY= ran; it arrived before the query resolved).
- Notifications can arrive at ANY time, including between queries and during one;
  they are not tied to a query result.
- Pool caveat =[DOC apis/pool]=: a LISTEN belongs to one physical connection; a pooled
  client that is released may be ended (idle timeout, =maxUses=) and the subscription
  with it; with =pool.query= each call may use a different client. A dedicated
  =Client= (or a checked-out pooled client that is never released while listening) is
  the only correct way. Notifications are lost while the connection is down; there is
  no replay.
- Payload limit is the server's (8000 bytes); not enforced client-side.

** 8.1 =DatabaseError= — verified shape
=[SRC pg-protocol/dist/messages.js:36-42]=, fields assigned at
=parser.js:296-324= =[OFFLINE]=: =class DatabaseError extends Error=;
=instanceof pg.DatabaseError= and =instanceof Error= both hold; =name= is the string
="error"=; =message= is the server's =M= field. Own enumerable keys (in order):
=length=, =name=, =severity=, =code=, =detail=, =hint=, =position=, =internalPosition=,
=internalQuery=, =where=, =schema=, =table=, =column=, =dataType=, =constraint=,

non-localized severity, is read into =severity= only through =S=; the parser keeps the
last of =S=/=V= it saw under their own letters, and =severity= is =fields.S=).
Observed: ={code "42P01", severity "ERROR", position "15"}= and a unique-violation
={code "23505", detail "Key (id)=(1) already exists.", schema "public", table "users",
constraint "users_pkey"}=.

A =DatabaseError= rejects the query it belongs to and does not touch the connection;
the transaction status becomes ="E"= inside a transaction (server rule) — =[OFFLINE]=
outside a transaction it stayed ="I"=.

** 8.2 Socket / Node errors
Plain Node errors propagate unchanged: =ECONNREFUSED= =[OFFLINE]= ={code:
"ECONNREFUSED", errno: -61, syscall: "connect", address: "127.0.0.1", port: 9,
message: "connect ECONNREFUSED 127.0.0.1:9"}=; likewise =ENOTFOUND=, =ETIMEDOUT=,
=ECONNRESET=, TLS errors (=CERT_*=, =DEPTH_ZERO_SELF_SIGNED_CERT=). =ECONNRESET= /
=EPIPE= are swallowed while ending (=connection.js:54-60=).

* 9. The fake-socket seam and the wire messages a fake needs
=[SRC pg/lib/connection.js:19-22]=: =new Client({stream})= accepts a Duplex stream or a
FUNCTION =(connectionConfig) => Duplex=; the Pool forwards the same option to each
Client, so a factory serves pools. The Client calls =stream.setNoDelay(true)=,
=stream.connect(port, host)= (or the socket path) and waits for =connect=;
=setKeepAlive=, =ref=, =unref=, =cork=/=uncork= (optional), =destroy=, =end= and the
=close= event (→ Client =end=) are used (=connection.js:40-65=, =client.js:169-182=).
=[OFFLINE]= the real Client ran the whole protocol against such a fake. The fake must
answer: startup → =R= AuthenticationOk (int32 0), =K= BackendKeyData, =Z=
ReadyForQuery('I'); a simple query =Q= → =T= RowDescription, =D= DataRow*, =C=
CommandComplete('SELECT n'), =Z=; the extended sequence =P B D E S= → =1= ParseComplete,
=2= BindComplete, =T=, =D=*, =C=, =Z=; errors → =E= ErrorResponse (letter-tagged
cstrings, =\0= terminated) then =Z=; notices =N=; notifications =A= (int32 pid, cstring
channel, cstring payload); =X= Terminate → close. Responses must be pushed
asynchronously (=setImmediate=), as a socket would; synchronous pushes inside =_write=
desynchronize the client (=[OFFLINE]= "Received unexpected rowDescription"). The
Phase 1 test fake is this table-driven socket, which exercises the real =pg= code
end-to-end without a server.

* 11. Consequences for the pg-cljs design

** 11.1 Key translation table (config in, data out)
Upstream mixes camelCase and snake_case, so the binding uses an EXPLICIT table, not
a generic kebab→camel rule:

| =:connection-string=                 | =connectionString=                     |

| =:client-encoding=                   | =client_encoding=                      |
| =:application-name=                  | =application_name=                     |
| =:fallback-application-name=         | =fallback_application_name=            |
| =:options=                           | =options=                              |
| =:statement-timeout= =:lock-timeout= =:idle-in-transaction-session-timeout= =:query-timeout= | =statement_timeout= =lock_timeout= =idle_in_transaction_session_timeout= =query_timeout= |
| =:connection-timeout-millis=         | =connectionTimeoutMillis=              |

Row objects: column NAMES are the caller's own SQL output names (aliases) and are
user data, not wire codes — whether rows are keyed by keyword-as-written or by
string, and whether =:row-mode :array= is the default, is a Phase 1 design decision
to record in the manual; column VALUES are never re-cased or re-typed (int8 and
numeric stay strings, Buffers stay Buffers, Dates stay Dates, JSON stays parsed JS
objects unless a =:types= provider says otherwise).

** 11.2 Results
=query= resolves with ONE result map for one statement and a VECTOR of result maps
for a multi-statement simple query (2.7); pg-cljs keeps that distinction visible
rather than flattening it. =rows= is a vector; =fields= a vector of field maps.

** 11.3 Async and sequencing
Every =connect= / =query= / =end= / =release= / pool =connect= / pool =end= returns a
promesa promise built with =p/create= around the native promise. pg-cljs does not
queue queries on one client beyond what the caller does (2.4.3 deprecation); the
docs say one query at a time per client, sequence with =p/let= or use the pool.

** 11.4 Events and channels
The binding attaches an =error= listener to every Client and Pool it creates (an
unhandled =error= event crashes Node). =notification= (and optionally =notice=) become
a core.async channel per client with a sliding buffer of 1024 by default
(=:buffer= option), delivering the kebab maps of 11.1; =end= closes the channel.
Pool events surface as one events channel per pool with =:event= =:connect= /
=:acquire= / =:release= / =:remove= / =:error= maps.

** 11.5 Errors
One taxonomy, =:type= under =:pg-cljs/=: =database-error= (a =DatabaseError=: all 8.1
fields kebab-cased, =:code= as the SQLSTATE string, =:cause= the upstream error),
=connection-error= (socket errors with =:code=, the termination / timeout strings of
8.3 with =:reason=, =:host= / =:port=), =pool-error= (release twice, after end, queue
timeout), =argument-error= (validation before anything upstream is called: values
not a vector, no text, bad option key), =config-error= (missing / malformed
connection settings resolved from the env). Synchronous upstream throws (2.4.1, 2.1,
3.2) are caught and rejected / rethrown as these. No default type-parser override
(=parseInt8= stays off), no retries, no invented timeouts: every timeout is the
caller's option with upstream's default (none).
